# analyzer

Анализатор. Python.

По результату прогона находит предел сервиса и ставит диагноз: почему сервис в него упёрся.

## Как считается предел

Ступени проверяются по порядку. Ступень считается отказом, если выполнено хотя бы одно:
- p99 больше порога (`--p99-ms`, по умолчанию 500 мс);
- пропускная перестала расти: прирост пропускной, делённый на прирост целевой нагрузки относительно предыдущей ступени, меньше `--min-gain` (по умолчанию 0.5). Для первой ступени сравнение идёт с нулём, то есть проверяется `throughput / target`.
- доля ошибок больше `--max-error-percent` (по умолчанию 1 %). Считается по количествам:
  `errors.count / request_count`. Это условие нужно потому, что `throughput_rps` включает неуспешные ответы: если сервис быстро отвечает 5xx, пропускная растёт и второе условие отказ не видит.

Отказ подтверждает **вторая подряд** ступень с отказом (#57), как автостоп на макете
`live-limit-found.webp`: один случайный выброс p99 не объявляется пределом.

- Две ступени подряд с отказом - предел найден и подтверждён (`confirmed`).
  Предел - целевая нагрузка ступени перед первой из двух, `failed_step_index` - первая из двух.
- Одиночный отказ, после которого ступень снова в норме, - выброс: анализ идёт дальше,
  а в `reasons` появляется предупреждение «ступень N - одиночный отказ… это не предел».
- Ступени закончились на единственной ступени с отказом - предел найден, но
  неподтверждённый (`confirmed=false`), уверенность диагноза низкая.
- Если отказа не было, предел не найден и известна только нижняя оценка - нагрузка последней ступени.

Прирост пропускной всегда считается относительно соседней предыдущей ступени,
в том числе после выброса.

`reasons` - сначала причины по каждой провальной ступени с её номером
(«ступень 7: p99 812 мс выше порога 500 мс»), затем предупреждения о выбросах.

## Диагноз v1

Метрик самого сервиса нет, поэтому диагноз ставится только по внешним признакам из
ступеней ([`analyzer/diagnosis.py`](analyzer/diagnosis.py)). Каждая провальная
ступень сравнивается с предыдущей:

| Признаки ступени | Причина | Полный набор признаков |
| --- | --- | --- |
| Ошибок больше порога, p99 не выше порога | `rejecting` - отклоняет нагрузку (5xx, лимиты) | Пропускная при этом растёт |
| p99 выше порога, скачок в 3 раза и больше или держится у потолка (две провальные ступени, p99 отличается не больше чем на 10 %, ошибок не меньше 1 %) | `slow_responses` - не успевает отвечать (очередь, ресурсы) | С задержкой растут и ошибки - таймауты |
| p99 выше порога, рост плавный, пропускная встала, ошибок мало | `saturation` - насыщение (CPU, пул соединений) | Да |
| p99 выше порога, рост плавный, пропускная не встала или есть ошибки | `slow_responses` | Нет |
| p99 не выше порога, ошибок мало, пропускная встала, а p99 растёт | `saturation` | Да |
| Пропускная встала, но p99 не растёт и ошибок мало | Ни одно правило | - |

Таймауты в `StepResult` не отделены от других ошибок, а таймаут агента анализатору
не известен. Поэтому «p99 упирается в таймаут» распознаётся по форме p99: скачок или
плато на двух провальных ступенях. Плато считается потолком, только если ошибок
не меньше 1 %: p99 у таймаута значит, что таймаутом кончился хотя бы 1 % запросов,
а таймауты входят в ошибки. Плато без ошибок - плавный рост при насыщении. Эта граница
следует из определения p99 и от `--max-error-percent` не зависит.

Итог:

- провальные ступени указывают на разные причины или ни одно правило не подошло -
  `inconclusive`, уверенность `low`;
- предел подтверждён, причина одна, у обеих ступеней полный набор признаков - `high`,
  иначе `medium`;
- предел неподтверждённый - причина по единственной провальной ступени, уверенность
  `low`, объяснение начинается с «Вероятно».

Диагноза нет, и это видно по статусу: `no_limit` - предел не найден; `too_few_steps` -
до первой провальной ступени меньше двух ступеней, не с чем сравнить.
`explanation` и `evidence` - текст для человека. CLI печатает те же объяснение и
признаки, что отдаёт сервис.

CLI учитывает `status`: для `aborted` явно сообщает, что прогон прерван и
анализируются только завершённые ступени. Если сохранённых ступеней нет,
сообщает, что предел определить нельзя. Для ступени с `request_count=0`
анализ завершается с ошибкой нехватки измерений, не объявляя предел сервиса.

Входные данные - `result.json` (пример - `testdata/results/limit-found.json`).
Если в нём нет нужного поля или вместо числа стоит строка, `null` и т.п., анализатор завершается с кодом 1 и сообщением, в какой ступени и каком поле ошибка.

Если `skipped_count` больше нуля, анализатор отклоняет измерения: агент не
подал всю запланированную нагрузку, поэтому нельзя объявлять предел сервиса.
Старые файлы без этого поля поддерживаются; новые результаты содержат
счётчик явно. Отображение protobuf в JSON описано в
[`proto/README.md`](../../proto/README.md).


## Запуск из командной строки

Нужен Python 3.10+, зависимостей нет. Команды выполняются из `services/analyzer`.

```bash
python -m analyzer ../../testdata/results/limit-found.json
python -m analyzer ../../testdata/results/limit-found.json --p99-ms 300 --min-gain 0.5
```

Через Docker из корня репозитория (путь к файлу относительно корня):

```bash
docker compose run --rm analyzer-cli testdata/results/limit-found.json --p99-ms 300
```

## gRPC-сервис

`python -m analyzer.server` отвечает на `AnalyzerService.FindLimit`
([`proto/bendmark/v1/analyzer.proto`](../../proto/bendmark/v1/analyzer.proto)).
Его вызывает координатор после завершения прогона. Алгоритм и диагноз те же, что у CLI.

```bash
pip install -r requirements-dev.txt   # grpcio, grpcio-tools, protobuf 1.70.0 / 5.29.3
python gen_proto.py                   # код из proto -> generated/ (не коммитится)
python -m analyzer.server --listen 0.0.0.0:50052
```

В Docker сервис `analyzer` из `docker-compose.yml` запускается сам при
`docker compose up`; код из proto генерируется при сборке образа.

`gen_proto.py` нужно запускать заново после изменения `.proto`. Тесты генерируют
код сами, если его ещё нет.

На Windows для grpcio 1.70 есть готовые сборки только до Python 3.13. На Python 3.14
pip пытается собрать пакет из исходников и требует компилятор C++. Создайте venv на
3.13: `py -3.13 -m venv .venv`.

| Ситуация | Ответ |
| --- | --- |
| Предел найден или нет | `OK`: `found`, `confirmed`, `limit_rps` (нижняя оценка, если `found=false`; нет, если отказ на первой ступени), `failed_step_index` (с единицы, только при `found=true`), `reasons`; `diagnosis` со статусом всегда |
| Нет ступеней, индексы не `1..N`, нерастущий `target_rps`, `errors.count > request_count`, нечисловые метрики, неверные пороги | `INVALID_ARGUMENT` |
| У ступени `skipped_count > 0` или `request_count = 0` | `FAILED_PRECONDITION`: измерения не определяют предел сервиса |

Порядок проверок: сначала форма запроса и пороги (`INVALID_ARGUMENT`), затем
пригодность измерений (`FAILED_PRECONDITION`), затем поиск предела.
Отсутствующий порог в `options` - значение по умолчанию (p99 500 мс, прирост 0.5,
ошибки 1 %); явно переданный ноль для доли ошибок сохраняется.

## Тесты

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
pytest
```

`tests/test_server.py` поднимает gRPC-сервер в том же процессе и проверяет, что
на каждом файле из `testdata/results/` сервис даёт тот же исход и диагноз, что CLI.
`tests/test_diagnosis.py` для каждого файла из `testdata/results/` проверяет
ожидаемые статус, причину и уверенность диагноза; новый файл без ожидания роняет тест.

Тесты читают общие результаты из [`testdata/results/`](../../testdata/results/).
Описание случаев и ожидаемых пределов - в
[`testdata/README.md`](../../testdata/README.md). Для проверки ошибок отдельных
полей тесты изменяют загруженную ступень в памяти. Хелпер `steps()` используется
для небольших проверок значений ровно на границе порогов и за ней.
