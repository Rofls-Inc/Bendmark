# load_agent

Генератор HTTP-нагрузки: проходит сценарий из ступеней, на каждой шлёт GET-запросы с заданной частотой, замеряет задержки и пишет полный result.json.

## Сборка

```bash
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . -j
```

Нужны: CMake ≥ 3.16, C++17, libcurl с заголовками (`libcurl4-openssl-dev` на Debian/Ubuntu).

## Запуск

Две формы: сценарий из ступеней или одна ступень (для отладки).

```
./load_agent <URL> --steps RATE:DURATION[,RATE:DURATION...] [options]
./load_agent <URL> <rate_per_sec> <duration_sec> [options]
```

Примеры:

```bash
./load_agent https://example.com --steps 100:45,200:45.5,300:30 --json result.json
./load_agent https://example.com 100 45.5 --json result.json
```

## Опции

| Опция | По умолчанию | Описание |
|---|---|---|
| `--steps LIST` | — | Ступени: `RATE:DURATION`, через запятую; длительность дробная |
| `--name NAME` | `cli` | Имя сценария в JSON |
| `--timeout MS` | `5000` | Таймаут одного запроса, мс |
| `--max-concurrency N` | `1000` | Потолок для авторазмера пула |
| `--concurrency N` | auto | Ручное переопределение числа воркеров (для отладки) |
| `--json FILE` | stdout | Куда писать result.json (без флага — в stdout) |

## Размер пула воркеров

Агент считает число воркеров сам, **на каждую ступень отдельно**:

```
W = min(ceil(target_rps × timeout_sec) + 1, max_concurrency)
```

Это гарантирует, что при исправном сервисе всем запросам хватит воркеров: `target_rps × timeout_sec` — сколько запросов может быть в полёте одновременно, если каждый висит до таймаута; `+1` — запас на тик; `max_concurrency` — предохранитель от тысяч потоков.

Примеры:

| `target_rps` | `timeout` | `W` |
|---|---|---|
| 100 | 5 с | 501 |
| 400 | 5 с | 1000 (упёрлись в `max_concurrency`) |
| 10 | 1 с | 11 |

Флаг `--concurrency N` **отключает авторазмер** и использует ровно `N` воркеров на всех ступенях — это для отладки и тестов, а не для прогонов.

Если сервис под нагрузкой отвечает дольше, чем `timeout`, часть запросов будет пропускаться — тогда стоит увеличить `--timeout` или `--max-concurrency`.

## Формат result.json

```json
{
  "scenario_name": "cli",
  "status": "completed",
  "steps": [
    {
      "index": 1,
      "target_rps": 100,
      "duration_seconds": 45,
      "request_count": 4500,
      "throughput_rps": 100,
      "latency_ms": { "p50": 12, "p90": 18, "p99": 22 },
      "errors": { "count": 0, "rate_percent": 0 },
      "skipped_count": 0
    }
  ]
}
```

| Поле | Описание |
|---|---|
| `scenario_name` | Имя сценария (`--name`) |
| `status` | `completed` — сценарий прошёл все ступени |
| `steps[].index` | Позиция ступени, с единицы |
| `steps[].target_rps` | Заданная частота |
| `steps[].duration_seconds` | Заданная длительность, дробная |
| `steps[].request_count` | Завершившиеся попытки: успехи, HTTP-ошибки, таймауты |
| `steps[].throughput_rps` | `request_count / duration_seconds` |
| `steps[].latency_ms.p50/p90/p99` | Перцентили задержки от запланированного момента (nearest-rank) |
| `steps[].errors.count` | HTTP 4xx/5xx, таймауты, транспортные ошибки |
| `steps[].errors.rate_percent` | Доля ошибок от `request_count`, до 1 знака |
| `steps[].skipped_count` | Тики, не отправленные из-за занятости воркеров |

## Семантика измерений

Задержка считается от **запланированного момента отправки** до ответа или таймаута, по всем завершившимся попыткам, включая неуспешные. Пропуски в задержки не входят.

Ступень с `skipped_count > 0` — полная ступень: агент выдаёт её как есть и переходит к следующей. Что с ней делать, решает координатор — сохраняет все, анализатору отдаёт только ступени до первой с пропусками. Агент сам не останавливается ни на пропусках, ни на ошибках сервиса.

## Коды возврата

| Код | Значение |
|---|---|
| `0` | Сценарий выполнен |
| `1` | Ошибка аргументов, парсинга `--steps` или записи файла |
