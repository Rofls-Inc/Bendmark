# load_agent

Генератор HTTP-нагрузки: шлёт GET-запросы с заданной частотой, замеряет время ответа сервера и пишет агрегированную статистику в JSON.

## Сборка

```bash
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . -j
```

Нужны: CMake ≥ 3.16, C++17, libcurl с заголовками (`libcurl4-openssl-dev` на Debian/Ubuntu).

## Запуск

```
./load_agent <URL> <rate_per_sec> <duration_sec> [options]
```

Пример:

```bash
./load_agent https://example.com 100 45 --concurrency 64 --json result.json
```

## Опции

| Опция | По умолчанию | Описание |
|---|---|---|
| `--concurrency N` | `16` | Число потоков-воркеров |
| `--timeout MS` | `5000` | Таймаут одного запроса, мс |
| `--output FILE` | stdout | Куда писать задержки (одна на строку, мс) |
| `--json FILE` | — | Куда писать агрегированную статистику |

## Вывод

**Задержки** — в stdout или в `--output`, по одной на строку, в мс с точностью до микросекунды (только успешные):

```
12.483
11.902
13.771
```

**Ошибки** — в stderr:

```
request failed: HTTP 500 (after 12.4 ms)
request failed: Couldn't resolve host name (after 3.1 ms)
```

**JSON** (`--json result.json`):

```json
{
  "target_rps": 100,
  "duration_seconds": 45,
  "request_count": 4500,
  "throughput_rps": 100,
  "latency_ms": { "p50": 12, "p90": 18, "p99": 22 },
  "errors": { "count": 0, "rate_percent": 0 }
}
```

### Поля JSON

| Поле | Описание |
|---|---|
| `target_rps` | Заданная частота |
| `duration_seconds` | Заданная длительность |
| `request_count` | Число завершившихся запросов (успех + ошибка) |
| `throughput_rps` | `request_count / duration_seconds` |
| `latency_ms.p50/p90/p99` | Перцентили времени ответа сервера |
| `errors.count` | Число неуспешных запросов |
| `errors.rate_percent` | Доля ошибок от завершившихся запросов, % |

## Коды возврата

| Код | Значение |
|---|---|
| `0` | Хотя бы один запрос успешен |
| `1` | Ошибка аргументов или файла |
| `2` | Все запросы провалились |
| `3` | Ни одного запроса не отправлено |

## Что именно измеряется

Замеряется **только время ответа сервера** (`service_time`): от фактической отправки HTTP-запроса до получения ответа. Ожидание свободного воркера в очереди в замер не входит.

Каждый тик по расписанию кладёт запланированный момент в очередь. Воркер берёт момент, отправляет запрос и записывает `service_us = конец_ответа − старт_отправки`. Значит:

- Ни один тик не пропускается: число запросов всегда равно `rate × duration`.
- Задержка не зависит от `concurrency` и от того, сколько запросов одновременно в полёте.
- Если воркеров мало и очередь растёт, это удлиняет прогон, но не искажает `latency_ms`.

## Выбор concurrency

Правило: `concurrency ≥ rate × средняя_задержка_в_секундах`, с запасом ×2–4.

`concurrency` не ограничивает число отправленных запросов — оно всегда `rate × duration`. Он определяет, сколько запросов обрабатывается одновременно; остальные ждут в очереди. При слишком маленьком `concurrency` прогон может занять **значительно больше** `duration`: все запросы будут поставлены в очередь, но воркеры разберут её позже. Например, при `rate = 100`, `duration = 10` (1000 запросов), `concurrency = 4` и ответе сервера за 2 с прогон займёт ~500 секунд.
