# Injector (Go)

TCP-прокси для экспериментов с неисправностями сети. Передаёт данные без
разбора протокола, задерживает ответы сервера, отклоняет новые соединения
или обрывает открытые соединения по таймеру.

## Параметры

| Флаг | По умолчанию | Что делает |
| --- | --- | --- |
| `-listen` | `127.0.0.1:8081` | Адрес прокси |
| `-upstream` | обязательный | Адрес сервера в формате `host:port` |
| `-delay` | `0` | Постоянная задержка каждого фрагмента ответа |
| `-jitter` | `0` | Случайная добавка к задержке в диапазоне `[0, jitter]` |
| `-drop-rate` | `0` | Вероятность немедленно закрыть новое TCP-соединение, от 0 до 1 |
| `-reset-after` | `0` | Обрыв обеих сторон соединения через указанное время после его принятия; `0` отключает режим |
| `-seed` | `1` | Зерно генератора случайности |
| `-health-listen` | выключен | Отдельный HTTP-порт с `GET /health` |
| `-healthcheck` | выключен | Проверить HTTP-адрес живости и завершиться с кодом 0 или 1 |

Для времени подходят значения `100ms`, `2s`. Задержки должны быть
неотрицательными, их сумма должна помещаться в `time.Duration`.

`delay + jitter` применяется **к каждому полученному фрагменту ответа**.
TCP не хранит границы HTTP-запросов: один ответ может состоять из нескольких
фрагментов. Задержка всего запроса может получиться больше `delay + jitter`.

`drop-rate=0.2` задаёт 20% вероятности отклонения каждого нового соединения.
Измеренная доля колеблется. HTTP Keep-Alive позволяет отправлять несколько
запросов по одному соединению, поэтому доля ошибок HTTP может отличаться от
`drop-rate`. `reset-after` отсчитывается один раз от принятия TCP-соединения,
включая время подключения к серверу; последующие HTTP-запросы таймер не обновляют.
Обрыв также отменяет ещё не закончившуюся задержку ответа.

Одинаковый `seed` воспроизводит случайные решения при одинаковом порядке
соединений и фрагментов. Каждое принятое соединение имеет свой генератор джиттера,
поэтому работа соседних потоков не меняет последовательность отклонений.
Границы TCP-фрагментов и планирование ОС могут различаться между запусками.
Перезапуск инжектора начинает последовательность заново.

## Запуск вручную

Сначала запустите ABStock на `http://127.0.0.1:5062`. Затем из
`services/injector`:

```powershell
go run . -listen 127.0.0.1:8081 -upstream 127.0.0.1:5062 -delay 100ms -jitter 50ms -seed 42
```

Примеры других режимов:

```powershell
go run . -upstream 127.0.0.1:5062 -drop-rate 0.2 -seed 42
go run . -upstream 127.0.0.1:5062 -reset-after 2s
```

Флаги можно комбинировать. Остановить прокси: `Ctrl+C`.
В другом терминале сравните прямой запрос и запрос через прокси:

```powershell
curl.exe -o NUL -s -w "time: %{time_total}s`n" http://127.0.0.1:5062/
curl.exe -o NUL -s -w "time: %{time_total}s`n" http://127.0.0.1:8081/
```

## Docker Compose и сравнение прогонов

Из корня Bendmark:

```powershell
docker compose up --build -d --wait --wait-timeout 180
docker compose ps abstock-slow
```

Сервис `abstock-slow` направляет трафик в тот же ABStock. Его настройки в
`docker-compose.yml`: `delay=600ms`, `jitter=100ms`, `seed=42`; отклонения и
обрывы по таймеру выключены. Параметры передаются через `command`.
С компьютера прокси доступен на http://localhost:8081.

Проверка через координатор в интерфейсе http://localhost:5173:

1. Создайте сценарий по `http://abstock:8080/`: метод GET, от 5 до 20 запросов/с,
   шаг 5, длительность ступени 3 секунды. Дождитесь завершения и анализа.
2. Повторите те же параметры с целью `http://abstock-slow:8081/`.
3. Сравните p99 и оценку предела в двух отчётах. При стандартном пороге p99
   500 мс и исправном ABStock прямой прогон обычно даёт нижнюю оценку
   `≥ 20 запросов/с`. Через прокси задержка превышает порог уже на первой
   ступени: отчёт покажет, что предел ниже 5 запросов/с.
4. Скачайте оба `result.json`, чтобы сохранить измерения. Точные значения
   задержек зависят от компьютера и границ фрагментов ответа.

Это эксперимент с влиянием задержки на результат нагрузочного теста.
Для другого режима измените `command` сервиса `abstock-slow` и выполните
`docker compose up -d abstock-slow`. Управление неисправностями через сценарий
и интерфейс планируется отдельно.

### Проверка живости

HTTP-проверка работает на отдельном порту внутри контейнера и не подвергается
неисправностям. Она проверяет живость инжектора, не создаёт соединений к
тестовой цели и не меняет последовательность случайных решений.
Даже при `drop-rate=1` контейнер остаётся `healthy`.

```powershell
docker compose exec abstock-slow /injector -healthcheck http://127.0.0.1:8082/health
```

Для локального процесса включите её через `-health-listen 127.0.0.1:8082`.

## Проверки

Из `services/injector`:

```powershell
go test ./...
go test -race ./...
go vet ./...
docker build -t bendmark-injector .
```

Для `-race` нужен C-компилятор. Тесты проверяют пересылку, задержку, границы
джиттера, воспроизводимость seed, долю отклонений на 1000 TCP-соединениях,
обрыв по таймеру, отмену ожидания ответа и независимую проверку живости.
CI запускает тесты с `-race`, `go vet`, собирает образ и проверяет healthcheck
запущенного контейнера с `drop-rate=1`.
