# Контракты gRPC v1

`bendmark.v1` описывает обмен координатора с агентом и анализатором.
В этой задаче есть схемы, генерация кода и проверки совместимости.
Рабочие gRPC-серверы и клиенты подключаются отдельно в #32–#34.

## Сценарий и агент

В v1 один агент исполняет один прогон за раз. `run_id` — UUID, созданный
координатором; он одинаков в `Run`, его ответах и `Stop`.
Сценарий содержит имя, абсолютный HTTP(S) URL и непустой список ступеней.
Нагрузка и длительность — конечные числа больше нуля.

Поддерживается только метод `GET` в верхнем регистре. Координатор отклоняет
другие значения в HTTP API с 400; будущий gRPC-агент обязан дополнительно
проверять метод в `Run` и возвращать `INVALID_ARGUMENT`.
Постоянная и убывающая нагрузка допустимы для запуска. Для поиска предела
анализатор требует отдельную рампу со строго возрастающим `target_rps`.

`Run` — поток ответов сервера. Агент отправляет ровно один `RunResponse`
на каждую полностью завершённую ступень, по порядку, с `index` от единицы.
Это позиция в исходном сценарии, а не индекс массива с нуля.
Координатор собирает эти ответы в итоговый массив `steps`.

### Статусы RPC и остановка

| Ситуация | Статус gRPC | Действие координатора |
| --- | --- | --- |
| Все ступени выполнены и отправлены | `Run`: `OK` | Прогон `completed` |
| Некорректный UUID, сценарий или неподдерживаемый метод | `Run`: `INVALID_ARGUMENT`, без нагрузки | Ошибка запуска, состояние `failed` |
| Новый `Run`, пока агент занят, в том числе с тем же UUID | `Run`: `RESOURCE_EXHAUSTED`, без очереди | Повторить позже или выбрать другого агента |
| Успешный `Stop` активного UUID | `Stop`: `OK`, `was_running=true`; исходный `Run`: `CANCELLED` | Прогон `aborted`, сохранить полученные полные ступени |
| `Stop` неизвестного или уже завершённого UUID | `Stop`: `OK`, `was_running=false` | Повтор безопасен; завершённый прогон не становится `aborted` |
| Некорректный UUID в `Stop` | `Stop`: `INVALID_ARGUMENT` | Не останавливать другие прогоны |
| Координатор отменил вызов `Run` | `Run`: `CANCELLED` | Прогон `aborted`, прекратить нагрузку |
| Истёк срок вызова `Run` | На стороне клиента `DEADLINE_EXCEEDED` | Прогон `aborted`, сервер обязан прекратить нагрузку |
| Внутренняя ошибка агента | `Run`: `INTERNAL` | Состояние `failed`; сохранить уже полученные измерения как диагностику |

Ошибки HTTP тестируемого сервиса и таймауты отдельных запросов входят в
метрики; они сами по себе не завершают RPC с ошибкой.

`Stop` прекращает планирование запросов, отменяет незавершённые попытки и
ждёт освобождения рабочих потоков. Ответ `Stop` приходит после прекращения
нагрузки. При отмене `Run` сервер выполняет ту же очистку, даже если клиент
уже закрыл поток и получить подтверждение не может.
Повторный `Run` после освобождения агента разрешён; это новый запуск,
автоматического воспроизведения старых ответов в v1 нет.

**Остановка посреди ступени:** неполная ступень в v1 не отправляется.
До остановки сохраняются только ранее отправленные полные ступени.
Если остановка пришла во время ожидания ответов текущей ступени, она тоже
считается неполной. Поэтому `duration_seconds` у каждого отправленного
результата равна плановой длительности соответствующей ступени.
Она описывает окно планирования, а не дополнительное время ожидания ответов.
Для частичных результатов потребуется отдельное обозначение и фактическая
длительность; их нельзя выдавать за полную ступень с плановой длительностью.

При гонке нормального завершения со `Stop` первое зафиксированное конечное
состояние определяет исход: уже завершённый `Run` остаётся `OK`, а `Stop`
возвращает `was_running=false`. При остановке активного прогона исход —
`CANCELLED`. Освобождение состояния прогона должно быть атомарным.

## Метрики ступени

- `request_count` — все завершившиеся попытки, включая HTTP-ошибки и таймауты.
- `throughput_rps = request_count / duration_seconds`.
- `skipped_count` — запланированные запросы, которые агент не отправил,
  потому что все рабочие потоки были заняты. Они не входят в `request_count`,
  задержки и ошибки. Это признак ограничения генератора нагрузки.
- `latency_ms` — перцентили по завершившимся попыткам, включая неуспешные.
  Время считается от запланированной отправки до ответа или таймаута.
- `errors.count` — HTTP 4xx/5xx, таймауты и транспортные ошибки;
  `0 <= errors.count <= request_count`.
- При ненулевом `request_count` доля ошибок равна
  `100 * errors.count / request_count`. При нулевом счётчике `errors.count`,
  `rate_percent` и все перцентили равны нулю. Это отсутствие измерений.

Чтение JSON анализатором уже отклоняет положительный `skipped_count` с
понятным сообщением. Старые файлы без этого поля читаются как раньше;
новые агенты должны передавать счётчик явно. В gRPC-обёртке #32 эту ошибку
измерений нужно перевести в `FAILED_PRECONDITION`.

## Анализатор

`FindLimitRequest.steps` — непустой последовательный префикс полностью
завершённых ступеней, с индексами `1..N` и строго растущим `target_rps`.
Префикс может быть получен от остановленного прогона: результат поиска
относится только к переданным ступеням. Статус всего прогона хранит координатор;
он должен явно обозначать прерванный прогон в отчёте.

| Ситуация | Результат |
| --- | --- |
| Отказ найден | `OK`, `found=true`, причины и `failed_step_index` |
| Отказ уже на первой ступени | `limit_rps` отсутствует |
| Отказа не было | `OK`, `found=false`, `limit_rps` — нижняя оценка, индекс отказа отсутствует |
| Пустые, некорректные или не возрастающие измерения; неверные пороги | `INVALID_ARGUMENT` |
| Хотя бы одна ступень имеет `request_count=0` или `skipped_count>0` | `FAILED_PRECONDITION`: нельзя приписывать ограничение генератора сервису |

`failed_step_index` — значение **`StepResult.index`, от единицы**.
Порог p99 по умолчанию 500 мс, минимальный прирост пропускной — 0.5,
максимальная доля ошибок — 1 %. Отсутствующее `options` или отдельное
`optional`-поле означает соответствующий порог по умолчанию.
Явно переданный ноль для доли ошибок сохраняется и означает запрет ошибок.
Равенство порогу допустимо: p99 и ошибки должны превысить порог,
а прирост пропускной должен стать меньше порога.

## Как получается result.json

Это отдельный формат Bendmark. Стандартный ProtoJSON использует ключи
`requestCount` и строковое представление `uint64`; он не подходит
непосредственно для входа текущего анализатора.
Даже сохранение исходных имён полей не превращает строки счётчиков в числа.
Правила ProtoJSON описаны в [документации Protobuf](https://protobuf.dev/programming-guides/json/).

Координатор собирает объект из полей сгенерированных классов явно:

| Поле protobuf | Поле JSON | Тип JSON |
| --- | --- | --- |
| `StepResult.index` | `index` | целое число |
| `target_rps`, `duration_seconds`, `throughput_rps` | те же имена | числа |
| `request_count`, `skipped_count` | те же имена | целые числа, включая ноль |
| `latency_ms.p50/p90/p99` | вложенный `latency_ms` | числа |
| `errors.count` | вложенный `errors.count` | целое число |
| счётчики запросов и ошибок | `errors.rate_percent` | число, округлённое до одного знака; при нуле запросов — 0 |

В C# следует создать отдельный DTO со свойствами JSON в `snake_case` и
числовыми счётчиками `ulong`, затем сериализовать его через `System.Text.Json`.
Не использовать protobuf `JsonFormatter` для итогового файла.
В Python проверяемый пример отображения находится в
[`result_json.py`](result_json.py):

```python
import json
from proto.result_json import run_to_json

# completed_steps: только полученные StepResult полных ступеней
data = run_to_json(scenario.name, "aborted", completed_steps)
text = json.dumps(data, ensure_ascii=False, indent=2, allow_nan=False)
```

Внешняя обёртка содержит `scenario_name`, `status` и `steps`.
`completed` ставится только после успешного завершения всего `Run`;
при остановке используется `aborted`, даже если сохранённые ступени без отказа.
Ошибку запуска или внутреннюю ошибку нельзя маскировать как `completed`:
координатор хранит `failed` и диагностические измерения отдельно.
Итоговый файл содержит нулевые поля явно. Браузер не должен преобразовывать
64-битные счётчики в неточные значения JavaScript `Number`.

## Генерация и CI

В корне находятся [`buf.yaml`](../buf.yaml) и [`buf.gen.yaml`](../buf.gen.yaml).
CI использует Buf **1.73.0**, генераторы сообщений Protobuf **29.3** и
генераторы gRPC **1.70.0** для C++, C# и Python.
Удалённые плагины Buf требуют доступа к `buf.build`; отдельный `protoc`
или системная установка gRPC-плагинов для этой проверки не нужны.
Результаты генерации лежат в игнорируемом `build/proto/` и не коммитятся.

После установки [Buf CLI](https://buf.build/docs/cli/installation/), из корня:

```powershell
buf build
buf lint
buf format --diff --exit-code
buf generate
```

В Windows проверка форматирования Buf требует `diff`. Она есть в Git for
Windows: можно запускать проверку из Git Bash или добавить его каталог
в PATH текущего PowerShell (для стандартного расположения Git):

```powershell
$env:PATH = "C:\Program Files\Git\usr\bin;$env:PATH"
```

Для проверки Python-кода после установки `proto/requirements-test.txt`:

```powershell
$env:PYTHONPATH = "build/proto/python"
python -m unittest discover -s proto/tests -v
```

Тесты проверяют настоящий обмен через сгенерированные gRPC-клиенты и
тестовые обработчики, поток `Run`, `Stop`, `FindLimit`, наличие optional-полей,
счётчик пропусков и преобразование в JSON с чтением анализатором.
Тестовые обработчики не реализуют нагрузку и алгоритм поиска предела.

В PR `buf breaking` сравнивает схему с коммитом основания PR, на push —
с предыдущим коммитом. При первом добавлении контрактов сравнивать ещё не
с чем: CI явно сообщает о создании исходной схемы. Ручной запуск без коммита
сравнения выполняет остальные проверки. Категория `FILE` обнаруживает
переименования, удаления и смену типов или номеров полей.
Новые поля получают новые номера; опубликованные номера нельзя переиспользовать.

Локальная проверка относительно текущего коммита:

```powershell
buf breaking --against '.git#ref=HEAD,subdir=proto'
```
